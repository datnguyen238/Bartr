# API contract

All marketplace routes are under `/api`. Authentication uses an HTTP-only opaque session cookie. No endpoint trusts a caller-supplied owner ID. Mutations require a same-origin request and closed schemas. Conflicts use 409; unauthorized/private records are inaccessible; provider/database failures use actionable 503 responses without raw secrets.

- `POST /auth/register`, `/auth/login`, `/auth/logout`; `GET /me`. The implemented `GET /me` includes `storage` as `dynamodb`, `mongodb`, `temporary-memory`, or `temporary-json`; this is operational status, not authorization or durability evidence.
- `GET/PATCH /profile`: own profile and private preferences only; writes require expected revision.
- `GET/POST /items`, `PATCH /items/{id}`: owner-only draft/update, public available-listing discovery. New publication and a published value change require the exact positive estimate from the owner's current image analysis; missing or mismatched estimates return `EVALUATION_REQUIRED` (422), and stale or changed evaluated details return `STALE_ANALYSIS` (409). Existing published values remain until changed.
- `POST /items/{id}/image`, `GET /images/{id}`: normalized owner upload and audience-checked image read. Published images follow the listing's same-community audience; owners and authorized historical-trade participants retain their respective access.
- `POST /items/{id}/analysis`: owner-only, revision-bound Gemini Search evaluation. The backend validates cited comparable candidates and computes a median only with at least three distinct compatible USD comparables of one price type. Search failures or insufficient evidence trigger an explicitly labeled image-assisted fallback; clarification remains explicit and no failure publishes the listing. If both paths fail, a 503 leaves the draft intact.
- `POST /preferences/interpret`: suggestions for review, no direct mutation.
- `POST /items/{id}/embedding`: owner-only, revision-bound Bedrock indexing. DynamoDB projections are separate from authoritative items.
- `GET /recommendations`, `POST /recommendations/dismiss`: authenticated, reciprocal eligibility and both gap limits; explicit missing-input/provider/index failure states. DynamoDB semantic mode lazily embeds a bounded same-community corpus, conservatively filters exclusions, and returns only the requester's public `matching_item_ids` and their `matching_item_revisions`. `SEMANTIC_CAPACITY`, provider failures and stale snapshots are explicit; `semantic=false` keeps exact-text matching.
- `GET/POST /trades`, `GET /trades/{id}`: participants only; manual proposals require explicit warning acknowledgement where needed.
- `POST /trades/{id}/actions`: counter, note, accept, decline, withdraw, cancel, handoff. Expected proposal revision and command ID required. All effects are atomically validated; replay cannot duplicate or re-open state.

The planned OpenAPI and implementation schemas are distinct; this artifact captures the implemented audience and state invariants. No cash or third participant is accepted.

The planned [OpenAPI](openapi.json) still describes a different analysis request (`source_revision`/`image_ids`, operation and precondition headers) and response shape. The current implemented route accepts `expected_revision` and returns the analysis record described above; the planned OpenAPI has not yet been reconciled and must not be used as the implemented contract for this endpoint.


## Approved DynamoDB login/photo valuation increment

The owner switched the requested backend persistence to DynamoDB. See [the bounded design and configuration](../../../docs/DYNAMODB-LOGIN-VALUATION.md). Existing account/session and item routes remain; this does not claim conformance with every future route/schema in the planned OpenAPI.

- `BARTR_STORAGE=dynamodb` selects the [schema-v1 entity adapter](../dynamodb-data-model.md) using the AWS credential chain and existing String `PK`/`SK` table. No table is provisioned and no existing application data is migrated automatically. Explicit `json`, `memory` and legacy `mongo` selection remain supported.
- `GET /me` reports `storage=dynamodb` in this mode; the landing/discovery client accepts all four storage labels. Non-Atlas storage uses exact-text discovery and omits Atlas indexing controls.
- `POST /items/{id}/analysis` searches for comparables, falling back to image-assisted evaluation on search failure or insufficient evidence. It persists a server-authored `analysis_id` bound to owner/item/image/revision and returns `estimate_minor` (positive USD cents or null), provenance, and available evidence. Fallback results carry `fallback_reason: comparables_unavailable` and no comparable sources. Both provider calls may fail, in which case the saved draft remains unchanged. Cited text is generated by the provider and is not an independent verification of the linked page.
- Missing optional specifications or unconfirmed functionality do not alone require a clarification. If the comparable search asks for clarification, the image-assisted path attempts a rough estimate; material contradictions or an unidentifiable item may still yield no estimate. Previously cached clarification results are retried on the next request.
- If the image model returns both a positive estimate and optional questions, the estimate is retained unless it flags a material conflict. Optional questions do not change owner-provided facts. A missing estimate or flagged material conflict remains unresolved.
- `PATCH /items/{id}` accepts optional `analysis_id`. New publication and published value changes require the exact current search-backed estimate or image-assisted fallback estimate and set assisted provenance. Unrelated, stale or mismatched analysis is rejected. Fallback estimates have `price_basis: image_assisted_estimate`, no comparable evidence or range, and retain their basis on the item as `value_basis`. Existing items without that optional field remain readable; no migration is required. Publication stays an explicit owner action.
- `GET /items/{id}` returns a visible listing or 404. Unreviewed analysis is not included for other members. Published value metadata does not grant access to private provider results.
- Offline fixture results and historical live evidence are scoped in [verification status](../../../docs/VERIFICATION.md). Live AWS/Gemini access and table-schema validation are not repeated as part of the profile merge.

# Live trade updates

For FR-015, FR-020 and FR-021, `WS /api/trades/{trade_id}/live` requires an allowed browser Origin and the existing session cookie. Only a trade participant receives the private current trade snapshot. The server rechecks session and participant access, and checks persisted revisions approximately every two seconds; the browser reconnects and replaces only older revisions. Writes remain on the existing authenticated HTTP action endpoint. This bounded polling bridge works across workers sharing the repository; it is not a durable in-memory message queue or a push notification service. Client-sent frames close the read-only connection. Deployment must proxy WebSocket upgrades on the same origin. Disconnects require reconnect; the saved history is the recovery source. Each connection adds repeated repository reads and has not been load tested.

- Evidence for the original backend increment and subsequent landing-page integration is tracked separately in [verification status](../../../docs/VERIFICATION.md). Moto coverage exercises the HTTP/authentication/listing/valuation contract; live AWS and Gemini outcomes require their own evidence.

# Preferences picker limitation

On 2026-11-15 the product owner requested preset-only interest and exclusion selection in the profile UI (FR-006). This is a presentation restriction, not a server-side validation or contract change: existing custom preferences remain visible and can be removed, and the API still accepts valid custom terms. It limits entry of unlisted specific products and exclusions compared with the approved FR-006 experience. The optional interpretation UI is hidden because it could add unlisted terms. Restore custom entry or expand the catalog to recover that experience; no stored data migration is needed.

For FR-003–FR-005, `POST /items/{id}/identify` accepts `expected_revision` and returns photo-derived draft suggestions for title, category and description only. It checks ownership and photo/revision before and after the provider call and does not persist provider output, set a value, or publish. The client starts identification after photo upload, fills only empty fields and leaves condition to the owner. Price estimation remains the existing separately requested, revision-bound search. Provider failure leaves the photo/draft intact. This additive route is absent from the planned OpenAPI and needs reconciliation before release.

## Listing detail choices

For FR-003–FR-005 the listing UI offers preset categories and conditions while retaining existing saved values. The API still accepts existing free-text fields. Photo identification may return title, category and description suggestions; only empty fields are populated, and the owner can correct them. The owner selects condition before requesting the separate estimate. The estimate is bound to saved item facts, and changes after estimation require another evaluation. A successful current estimate is populated automatically for review before explicit publication. Historical analyses without suggestions remain valid. The preset choices restrict new free-text condition and category entry; details can be described in the item description, and restoring free-text entry requires only a presentation change.

When an evaluation has insufficient evidence, `evidence` may include validated partial comparable records, labelled by price type and condition. These records do not constitute an estimate and do not satisfy publication requirements. Rejected evidence remains excluded.

For FR-004 and FR-005, search timeouts trigger image evaluation. The search provider uses one shared 75-second default deadline for search and extraction, and image evaluation can make one additional bounded attempt when an identifiable item has no estimate. The valuation client deadline is 200 seconds. If evaluation is unavailable, the draft is retained; a timeout does not establish whether the provider billed an interrupted request.

For FR-005, comparable research may include a similar model of the same type, including a similar product from the same brand, rather than requiring an exact model or colorway. A brand match alone does not make an unrelated product comparable. Search evidence remains model-assessed; each newly extracted candidate may state `match_kind` (`exact`, `similar`, or `unknown`), and estimates including similar or unknown matches are low-confidence. Three distinct compatible cited USD offers of one price type remain required; previous records without `match_kind` are treated as unknown. The planned OpenAPI does not yet describe this additive response field.

The product owner requested a single estimate button and automatic price population on 2026-11-15. The UI may preselect a successful current estimate; the explicit publication action remains the owner's review and confirmation. The backend still validates the current analysis, exact estimate and unchanged facts. A stale or insufficient result is never auto-applied.
