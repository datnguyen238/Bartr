# Research: Bartr Smart Bartering Marketplace

**Date**: 2026-11-14 | **Input**: [spec.md](spec.md) | **Status**: complete for Phase 1 design

These are implementation decisions for the initial pilot, not claims that the feature exists. Three independent research tracks covered transaction integrity, AI integrations, and bundle optimization. Sources below are primary documentation checked for this plan. Algorithm and serialization choices are application-design inferences, not guarantees supplied by a provider.

## R1 — Preserve the foundation and use supported runtimes

- **Decision**: Extend the existing Python/FastAPI backend and Next.js App Router frontend. Keep the observed Python 3.14 baseline, FastAPI 0.163/Pydantic 2, Next.js 16.4.6/React 19.3.1, TypeScript 5.9, Tailwind 4 and shadcn components. Target Node 24 LTS and update the current Node 20 `.nvmrc` during implementation. Retain one root `requirements.txt`; lock exact compatible Python dependencies after a clean install and preserve the npm lockfile. Pin the local database image by digest in implementation.
- **Rationale**: Reuse the working foundation. Local Node 25 is not the planned reproducible runtime; the repository's Node 20 default has reached end of life. Current PyMongo/Pillow documentation includes Python 3.14 support. Dependency installation and import verification are implementation gates, not reasons to replace the stack.
- **Alternatives considered**: Rebuilding the frontend, an ORM, or a new API framework adds no specified capability. An unsupported Node baseline is avoidable.
- **Sources**: [Node release schedule](https://github.com/nodejs/Release), [PyMongo compatibility](https://www.mongodb.com/docs/drivers/compatibility/?driver-language=python), [Pillow Python support](https://pillow.readthedocs.io/en/stable/installation/python-support.html), [Next installation requirements](https://nextjs.org/docs/app/getting-started/installation).

## R2 — Accounts and server-authoritative sessions

- **Decision**: Use email/password accounts with `pwdlib[argon2]` hashes and opaque database-backed sessions. Generate 256-bit random session secrets; store only their digests, member reference, creation and absolute expiration (7 days). Rotate on register/login and revoke on logout. Production uses an HttpOnly, Secure, SameSite=Lax, host-only `__Host-bartr_session` cookie with Path=/; localhost uses `bartr_session` without Secure. No browser local-storage tokens.
- **Decision**: `GET /api/auth/session` supplies the current member or null plus a CSRF token derived from the opaque session secret and a server secret. It may establish an anonymous one-hour session for register/login protection. Every cookie-authenticated mutation, including login/register/logout, validates an exact allowed Origin and `X-CSRF-Token`. Backend authorization checks every owner/participant operation. Next rewrites remain transport; private responses are no-store and serialization allowlists exclude private fields.
- **Rationale**: Immediate revocation and one authority are simpler for the existing FastAPI API. Email is a private sign-in identifier, not a university verification claim. Normalize it consistently and enforce uniqueness. Use generic login failures; bound password lengths to 12–128 characters and session attempts. Password reset, email delivery, social login and eligibility verification are not silently added.
- **Alternatives considered**: JWT/refresh-token rotation and third-party identity services add machinery or new vendors without a specified need. Frontend route checks alone do not authorize API access.
- **Sources**: [FastAPI password hashing](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), [Next authentication and authorization](https://nextjs.org/docs/app/guides/authentication). The opaque-session/CSRF protocol and durations are this plan's decisions.

## R3 — MongoDB authority and bounded image storage

- **Decision**: One application-scoped PyMongo `AsyncMongoClient`, with an Atlas replica-set deployment. Use native collections, explicit indexes and validation schemas; no ODM. Transactions use primary reads, snapshot read concern, majority write concern and sequential operations.
- **Decision**: Store each sanitized image in a separate BSON binary document, maximum 4 MiB after processing, maximum four images per item. Accept JPEG/PNG/WebP, validate decoded content and a 20-megapixel limit, orient then re-encode with Pillow, strip metadata, and reject oversized/invalid uploads with actionable errors. Upload request limit is 8 MiB. Serve bytes only through an authorized image endpoint. Historical offer snapshots retain references; removal from discovery does not erase a participant's reviewed history.
- **Rationale**: Capped images fit below MongoDB's document limit and avoid a fourth cloud/storage service in the pilot. Images are not embedded in item/offer documents or loaded by matching queries. Unattached images are eligible for cleanup after 24 hours; referenced historical images are retained with the trade. No extra item-image transaction protocol is needed.
- **Alternatives considered**: GridFS does not support multi-document transactions and is unnecessary for these bounded objects. S3 is a future storage option when image volume warrants it, not an initial dependency.
- **Sources**: [PyMongo transactions](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/crud/transactions/), [GridFS and small files](https://www.mongodb.com/docs/manual/core/gridfs/), [FastAPI file handling](https://fastapi.tiangolo.com/tutorial/request-files/).

## R4 — Correct trade serialization and permanent invalidation

- **Decision**: Item documents carry `trading_revision`, monotonic `availability_epoch`, state and one `reserved_trade_id`. Offers capture item revisions/epochs, immutable reviewed facts, and participant hard-policy revisions. A Mongo transaction commits agreement and every reservation together or none.
- **Decision**: Proposal creation/replacement and every command on an open trade, including acceptance, notes, withdrawal and decline, write both participant guard documents in sorted member-ID order. A hard-policy update writes its member's guard, and item edits/removal write their owner's guard as well as the item. Trade transitions also conditionally write the current trade revision. This prevents policy/item invalidation from racing open-history appends as well as acceptance; agreed/awaiting-handoff actions serialize on their trade because later policies do not change their accepted terms. Snapshot reads alone are insufficient for cross-document policy changes.
- **Decision**: Community/exclusion edits append immutable hard-policy revision snapshots in the same transaction as their member update. Offer reads and acceptance inspect intervening revisions; any historically incompatible revision permanently invalidates the offer, even if a policy is later restored. Compare community revisions against the original common community captured in the offer, so both members later moving cannot revive it. Item revision/epoch changes likewise invalidate old offers after reserve/cancel restoration. Derive effective invalidation immediately on reads; a resumable projection worker may materialize it, but correctness never waits for that worker. Positive-interest/value-gap changes affect recommendations without invalidating otherwise eligible manual offers.
- **Rationale**: Avoid snapshot write skew and unbounded fanout updates. A participant changing exclusions and changing them back must not revive a closed offer. Agreements preserve accepted snapshots and ignore later preferences; reserved item details remain fixed.
- **Alternatives considered**: Independent item updates permit partial commitments. In-memory locks fail across instances. Invalidating every proposal for an unrelated preference edit unnecessarily changes the specified behavior.
- **Sources**: [Transaction production considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/), [snapshot read concern](https://www.mongodb.com/docs/manual/reference/read-concern-snapshot/). Guard writes and policy history are the designed application protocol.

## R5 — Retry receipts and unresolved operations

- **Decision**: Authenticated mutations require an `Idempotency-Key` scoped to the member, with a request digest covering method, path, expected revision and body. A unique command receipt prevents reuse with different content. Receipt result and domain mutations commit together; retain durable trade-action receipts with trade history. Return the prior outcome for an identical replay before checking stale HTTP preconditions.
- **Decision**: If commit outcome cannot be established, return 202 with an operation reference and `outcome=unresolved`; clients retain the same key, poll `GET /api/operations/{key}`, or retry the identical command. Absence of a visible receipt is also unresolved, never proof of failure. Retry on the same unique key cannot create a second effect. Driver callbacks contain no network AI calls or other external side effects. Apply a bounded transaction/HTTP deadline and resume reconciliation rather than waiting indefinitely.
- **Rationale**: Network failures and driver transaction retries must preserve accurate outcomes. A receipt alone outside the business transaction cannot prove the mutation occurred.
- **Alternatives considered**: Retrying under a new key, marking timeout as failure, or process-local deduplication permits duplicate or contradictory outcomes.
- **Sources**: [PyMongo transaction callbacks](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/crud/transactions/), [async session retry behavior](https://pymongo.readthedocs.io/en/stable/api/pymongo/asynchronous/client_session.html).

## R6 — Reviewed semantic facts and hard constraints

- **Decision**: Preferences explicitly distinguish `specific_product` and `category`. Use a versioned catalog for communities, categories and condition values; normalized product types and optional brand/model constraints are owner-reviewed attributes. Exclusions are structured conjunctions over reviewed category/condition/brand attributes. A phrase such as “damaged electronics” is suggested as electronics AND needs_repair and requires member confirmation. Provide manual entry when assistance fails; do not silently accept unrepresentable or contradictory exclusion text.
- **Decision**: Gemini proposes normalization; Titan/Atlas supplies semantic relevance candidates. Confirm relevance from reviewed canonical facts, known synonyms and a versioned/evaluated similarity threshold where exact facts are insufficient. Thresholds are calibrated against the independently labeled evaluation set, not treated as universal constants. A specific-product tier requires the saved product constraints to match; a high broad-category embedding score alone is insufficient. Unknown facts required by an exclusion fail closed with incomplete-information guidance.
- **Rationale**: Hard eligibility must be reproducible; semantic similarity must not decide whether an explicit exclusion can be ignored. Category and product interests remain alternatives, as specified.
- **Alternatives considered**: Raw string equality misses synonyms. A single opaque similarity score cannot guarantee exclusions or the chosen ranking.

## R7 — Deterministic bounded bundle optimization

- **Decision**: After item eligibility/relevance filtering, enumerate subsets of sizes 1–3 independently for each direction of each candidate pair. Thirty items yield 4,525 subsets per side. Partition by whether a recipient receives at least one specific-product match, sort totals, and use binary-search neighbor streams plus a bounded top-result heap. Do not allocate the 20,475,625-pair Cartesian product.
- **Decision**: Values are integer USD cents and tolerances integer basis points. For positive totals x,y and t=min(two member limits), require `abs(x-y)/max(x,y) <= t`. With t<1, feasible y lies in `[(1-t)x, x/(1-t)]`; t=1 permits all positive totals. Compare integer cross-products exactly; round only displayed percentages. Rank by recipients-with-specific-match descending (2,1,0), then exact relative gap ascending. Equal tier/gap has no required further ordering.
- **Decision**: Default response limit is 10, maximum 20. Continue past member-dismissed combinations. Search whole authoritative eligible community inventory within the 1,000-listing pilot envelope before declaring `no_match`; Atlas ANN accelerates partner discovery but is not completeness evidence. Missing/stale semantic artifacts or a deadline/index failure that prevents complete evaluation produces an unavailable result, not `no_match`. Above the measured envelope, fail explicitly rather than silently truncate.
- **Rationale**: Satisfy all nine shapes and the clarified order with bounded memory. Precomputed item/preference embeddings and reviewed facts keep provider latency off the recommendation critical path. Exact full-library optimality is not promised.
- **Alternatives considered**: One-to-one matching misses the innovation; LLM-authored bundles cannot guarantee constraints; weighted semantic/value scoring contradicts option A; exhaustive pair materialization wastes memory.
- **Evidence**: The research agent's throwaway math prototype agreed with exhaustive rational comparisons in 2,000 seeded random cases at 0/20/50/100% limits. This is design evidence, not implementation or load validation. [Atlas ANN/ENN semantics](https://www.mongodb.com/docs/vector-search/query/aggregation-stages/vector-search-stage/), [retrieval accuracy evaluation](https://www.mongodb.com/docs/vector-search/query/improve-accuracy/).

## R8 — Gemini integration and data boundary

- **Decision**: Use server-only `google-genai` async calls with JSON-schema/Pydantic output validation. Configure a stable explicit model, currently `gemini-3.8-flash`, rather than a preview/latest alias. Record model, prompt and schema versions. Return candidate attributes, uncertainty reasons and nullable USD estimate; require owner review before publishing. No verified market-price, authenticity or working-condition claims are inferred from a photo.
- **Decision**: Generate trade wording only from approved item facts and the relevant interest matches; validate referenced IDs and fall back to deterministic grounded explanations. Never send account/session identifiers, credentials or private trade notes to either AI provider. Treat text in listings/images as untrusted data, expose no model tools and reject invented facts/IDs.
- **Decision**: The live pilot is restricted to adults 18+ (self-attestation, no date of birth collection) and a supported provider region, with a paid Gemini project for real member content. This makes the brief's young-adult pilot explicit; no university verification or new per-action approval flow is required. Fixture development contains only synthetic content. Do not promise zero provider retention.
- **Rationale**: The current model page supports images and structured output. Provider terms impose age/data conditions; paid use avoids sending real member information through unpaid content-improvement terms. This is a delivery dependency for the requested integration.
- **Alternatives considered**: The older `google-generativeai` client, preview models, automatic provider switching, unvalidated JSON or free-tier real personal content are unsuitable here.
- **Sources**: [Python SDK](https://github.com/googleapis/python-genai), [stable Gemini model](https://aistudio.google.com/docs/models/gemini-3.8-flash), [structured output limitations](https://aistudio.google.com/docs/structured-output), [API terms](https://aistudio.google.com/docs/terms), [deprecations](https://aistudio.google.com/docs/deprecations).

## R9 — Titan and Atlas semantic contract

- **Decision**: Boto3 Bedrock Runtime `InvokeModel`, model `amazon.titan-embed-text-v2:0`, explicit region, `dimensions=1024`, `normalize=true`, float output. Validate 1,024 finite values and nonzero norm. Limit normalized application text to 8,000 characters; never send full inventories or private notes. SDK blocking calls run in a bounded thread pool.
- **Decision**: Persist embedding model/dimension, normalized text hash, source revision and status. Publish completion with a source-revision compare-and-set so old enrichment cannot overwrite newer text. Atlas vector index uses cosine and filter fields for community, owner, availability, and model version. Rehydrate results from authoritative records. Exact cached-vector fallback handles index lag in the pilot; fixture embeddings do not establish live semantic quality.
- **Rationale**: Titan V2's documented output dimensions align with the explicit vector index. Avoid repeated provider work on recommendation requests and mixed embedding spaces.
- **Alternatives considered**: Smaller vectors introduce a separate quality tradeoff; replacing Bedrock with Gemini embeddings disregards the requested division of responsibilities.
- **Sources**: [Titan model contract](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html), [request parameters](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-titan-embed-text.html), [InvokeModel](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html), [Atlas vector index](https://www.mongodb.com/docs/vector-search/indexes/vector-search-type/).

## R10 — Bounded work, recovery and observability

- **Decision**: Recommendation processing deadline is 9 seconds, leaving response overhead within SC-005. Image analysis deadline is 20 seconds; embedding attempts total at most 3 seconds with at most one transient retry inside that budget. Bound SDK hidden retries. No provider call occurs in a trade transaction. Durable Mongo enrichment jobs use leases, source revisions and backoff; one small worker process handles pending enrichment/invalidation without Redis/Celery.
- **Decision**: Pilot defaults: 20 recommendations/minute/member, 10 image analyses/hour/member, 120 trade commands/minute/member, and 5 login failures/15 minutes/account-plus-network digest. Return 429/Retry-After; use database-backed counters across workers and HMAC network identifiers rather than stored raw IPs. Limits are configuration, not silent data loss or lowered eligibility.
- **Decision**: Process restarts must not lose majority-acknowledged domain writes; ambiguous actions remain reconcilable by key. For a hosted pilot, target 99.5% monthly application availability, restoration within 4 hours and disaster-recovery data loss of at most 1 hour using verified database backups. Those operational targets require restore rehearsal and an appropriate Atlas backup-capable deployment; no cluster or paid resource is provisioned by this plan. After a restore, suspend trading until reservations, receipts and history are reconciled.
- **Decision**: Record event type, correlation/operation ID, timestamps, duration and sanitized outcome/error category. Measure recommendation latency, no-match vs failure, provider timeout/throttle, incomplete embeddings, constraint rejections, transaction retries and unresolved operations. Exclude prompts, item images/descriptions, private notes, raw email/IP, passwords, session and CSRF values from logs. Operational events expire after 30 days; auth/rate-limit records expire according to their purpose. Trade history and referenced policy/image/receipt evidence stay for the pilot; deletion/retention expansion needs its own specified workflow.
- **Rationale**: Resolve the operational details deferred during clarification without introducing a new platform. Deadlines and resumable records bound dependency failures and preserve integrity.
- **Alternatives considered**: In-process fire-and-forget jobs lose work on restart; automatic agreement expiration or support-driven forced handoff changes the product rules.
- **Sources**: [Atlas backup guidance](https://www.mongodb.com/docs/atlas/architecture/current/backups/), [Bedrock failure categories](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html). Numerical budgets are plan targets, not provider guarantees.

## R11 — Local reproducibility and release evidence

- **Decision**: Add a digest-pinned `mongodb/mongodb-atlas-local` Compose service with persistent db/config/search volumes, hostname configuration and host URI `mongodb://localhost:27017/?directConnection=true`. Bind localhost; local development credentials are placeholders only. It supplies real transactions and Search/Vector Search. A plain replica set is acceptable only for transaction-only tests, never as evidence of Atlas vector coverage.
- **Decision**: Keep pytest/httpx for domain/API tests; add Hypothesis for subset/ranking properties and Playwright with axe for browser/accessibility checks. Add deterministic provider adapters that reject outbound requests in fixture mode. Test HTTP contracts against the versioned OpenAPI design, real reservation races and uncertain commits, image access after removal, semantic freshness, and the 40-case/20-wording acceptance sets. Live connectivity smoke uses synthetic input and is opt-in; release semantic-quality and pilot usability outcomes are separate gates.
- **Rationale**: Foundation-only unit tests cannot prove transactions, search contracts or the central user journeys. A local compatible database avoids paid calls in ordinary verification.
- **Alternatives considered**: Mocks-only transaction tests, fake authenticated headers, and fixtures reported as live AI quality would provide misleading evidence.
- **Sources**: [Atlas Local Compose](https://www.mongodb.com/docs/atlas/cli/current/atlas-cli-docker-compose/), [local Docker deployment](https://www.mongodb.com/docs/atlas/cli/current/atlas-cli-deploy-docker/).
